# 耗时与优化 / Time budget

这个 skill 里**最贵的从来不是剪辑**。下面是一台真实机器的实测数据，以及每一项能砍掉多少。

Every number below is measured, not estimated, on this machine:

| 项目 | 值 |
|---|---|
| CPU | Intel Xeon Platinum，**2 核 4 线程** |
| 内存 | 7.7 GB |
| 独显 | **无**（无 CUDA） |
| 源素材 | 手机竖拍 720×1280 / 30fps / HEVC / **118 秒** |
| 成片 | 55.8 秒 / 720×1280 / 30fps |

---

## 一、实测耗时明细

| 步骤 | 耗时 | 占比 | 能否优化 |
|---|---|---|---|
| **语音转写**（medium 模型 / CPU） | **15.6 min** | 35% | ✅ **完全可以省掉**，见第二节 |
| 静音分析 + 定切点 | ~2 min | 4% | 已是最优 |
| 切割重编码 | 6.8 min | 15% | 换流复制可降，但会牺牲帧精度 |
| **逐帧渲染花字**（Remotion / Chromium） | **18.4 min** | 41% | ✅ **快 22–25 倍**，见第三节 |
| 字幕修正、音频标准化、校验 | ~2 min | 4% | — |
| **合计** | **≈45 min** | 100% | 优化后 **≈10 min** |

**两个瓶颈占了 76%：转写 + 渲染。** 其余所有步骤加起来不到 11 分钟。

优化前后对比（同一支片子）：

| | 现在 | 优化后 |
|---|---|---|
| 转写 | 15.6 min | **0**（用你已有的时间码） |
| 渲染 | 18.4 min | **0.8 min**（换 FFmpeg 单遍） |
| 其他 | 11 min | 11 min |
| **合计** | **≈45 min** | **≈12 min** |

素材变长时，差距会指数级放大。**30 分钟的源素材**：Remotion 路线约 **5.6 小时**，FFmpeg 路线约 **15 分钟**。

---

## 二、最大的浪费：在这个 skill 里转写

**这个 skill 不转写。** 它从「你已经有逐词时间码」开始工作。

原因很直接：本地转写很慢（上面 15.6 分钟只是为了 118 秒素材），而且**精度通常不如你手边已有的工具**。转写不是这个 skill 的强项，剪辑才是。

**如果你没有时间码**，两条路：

| 方案 | 代价 |
|---|---|
| 用自己的 ASR（云端 API / 本地大模型 / 字幕文件） | 最快，且精度更高 |
| 在这个环境跑一次转写 | 按上表计费：约 **0.13 × 素材时长（分钟）** 的 CPU 时间 |

时间码必须满足：

- **逐词级**（`{word, start, end}` 或 WhisperX 风格的 `segments[].words[]`）。整句级也能出片，但关键词变色就没法落到词内。
- **对应原始视频的绝对时间轴**。如果是转码版本产出的时间码，会有偏移，需要重新对齐。

> 转写精度不足会连锁触发 `TRAPS.md` 第 1、2 条（中文拆单字 → 修正失效 → 补丁又引入新问题）。**时间码质量决定整条流水线的上限。**

---

## 三、第二大浪费：用浏览器逐帧渲染

同一支 55 秒成片，两条路线的实测差距：

| 路线 | 耗时 | 相对实时 | 逐词高亮 |
|---|---|---|---|
| Remotion（Chromium 逐帧截图再编码） | **18.4 min** | 0.05x | ✅ 网页动画级 |
| **FFmpeg 单遍（本 skill 默认）** | **0.8 min** | 1.1x | ✅ 字幕级 |

**22–25 倍差距，不在机器，在路线。** Chromium 要把每一帧送进浏览器截图再编码；FFmpeg 是一遍滤镜直接出片。

分辨率对 FFmpeg 路线的影响（同一素材）：

| 分辨率 | 耗时 | 渲染速度 |
|---|---|---|
| 480p | 45.6 s | 11.3 帧/秒 |
| 720p | 83.3 s | 6.2 帧/秒 |
| 1080p | 155.5 s | 3.3 帧/秒 |

**结论：需要网页动画级效果才用 Remotion，否则一律 FFmpeg 单遍。** 竖版短视频的花字用 FFmpeg 完全够。

另外三条实测经验：

1. **切割、提速、烧字幕、响度标准化合并成一次 pass**，不要分四次编码。
2. **`-c copy` 做无损切割**只在切点正好落在关键帧上时才精确；要帧级精度就重编码，但别为此多编一遍。
3. **别在 4K 上做逐帧渲染**。分辨率翻倍，渲染时间大致平方增长。

## 四、容易低估的三项

### 1. 磁盘空间（会直接失败）

下载转写模型时报 `No space left on device`——C 盘只剩 3.4 GB，而模型要 3 GB。

**开工前先看剩余空间**，把工作目录和模型缓存都放在大容量盘：

```bash
# 模型缓存重定向（避免默认写系统盘）
HF_HOME=/path/to/big-drive/model-cache
```

大模型（large-v3 约 3 GB）在小内存机器上还会触发换页。**内存 < 8 GB 时用 medium 或更小。**

### 2. 长素材的上下文窗口（AI 助手的瓶颈）

转写稿要送给 AI 助手去读、去写稿。**1 小时以上的素材，转写稿可能塞不进单次上下文。**

这是"提炼重点"这一步的真正瓶颈——不是算力，是上下文长度。对策：分段处理，每段独立出一稿，最后人工合并顺序。

### 3. 反复出片的时间（AI Agent 特有）

一次调字幕、一次改剪点、一次换封面样式，各要多久？

| 操作 | 耗时 |
|---|---|
| 重建字幕时间码（`build.py`，不含渲染） | **秒级** |
| 换封面样式（`cover.py`） | **秒级** |
| 换字幕字号/颜色（`render.py` 重新出片） | **约 1 分钟** |
| 改剪点（要重新切割 + 出片） | **约 2 分钟** |

**所以：把判断放在便宜的那一步。** `build.py` 打印稿子和字幕行是秒级的，渲染是分钟级的——**先在稿子层面把逻辑和断句看对，再渲染。** 这正是 `--list-only` 和"先写稿再剪"流程存在的意义。

---

## 五、一句话总结

> **省时间的关键不是让剪辑更快，是别做那些不值得做的事：不要在这里转写，不要用浏览器渲染。**

按重要性排序的三个动作：

1. 用你已有的逐词时间码，**不要重新转写**（省 35%）
2. 用 FFmpeg 单遍出片，**不要逐帧渲染**（省 41%）
3. 在**稿子层面**反复改，最后才渲染（省掉 N 次重复出片）
